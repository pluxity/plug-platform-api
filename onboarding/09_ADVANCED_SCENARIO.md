# 9단계: 종합 실전 시나리오 (Real-world Scenario)

마지막 단계에서는 지금까지 배운 모든 지식을 총동원하여 실제 서비스에서 발생할 법한 요구사항을 해결합니다.

## 목표
- 데이터 수집, 도메인 로직, 알림 시스템의 통합.
- 이벤트 기반 아키텍처(Event Driven) 맛보기 (선택 사항).
- 전체 시스템의 흐름을 조망하는 능력 배양.

## 시나리오 설명
**"지하철 역(`Station`)의 공기질(`ClimateData`)을 모니터링하고, 특정 기준을 초과하면 관리자에게 알림을 보내는 시스템을 구축하라."**

## 요구사항

1.  **데이터 수집**:
    - 5단계에서 만든 Collector를 활용하여 주기적으로(예: 스케줄러 사용) 가상의 공기질 데이터를 수집합니다.
    - 수집된 데이터는 `ClimateData` 엔티티로 저장됩니다.
    - 각 데이터는 특정 `Device`와 연결되어 있고, 그 `Device`는 특정 `Station`에 설치되어 있다고 가정합니다.

2.  **임계치 확인 및 알림**:
    - 수집된 데이터 중 미세먼지(PM10) 농도가 80 이상이면 '나쁨' 상태로 판단합니다.
    - '나쁨' 상태가 감지되면, 해당 `Station`을 관리하는 담당자(`User`)에게 알림을 생성해야 합니다.
    - (알림 발송은 실제 이메일/SMS 대신 로그 출력이나 `Alert` 테이블 저장으로 대체합니다.)

3.  **조회 API**:
    - 현재 '나쁨' 상태인 역의 목록과 가장 최근의 미세먼지 수치를 조회하는 API를 만드세요.

## 실습 과제

### 과제 1: 통합 서비스 구현
1.  **브랜치 생성**: `onboarding/step-9-scenario` 브랜치를 생성하세요.
2.  **스케줄러 설정**: Spring `@Scheduled`를 사용하여 1분마다 데이터를 수집하는 Job을 만드세요.
3.  **로직 구현**:
    - 수집 -> 저장 -> 분석 -> 알림 흐름을 연결하세요.
    - `ClimateDataService`에서 데이터를 저장한 후, 값을 체크하여 `AlertService`를 호출하는 구조를 설계하세요.

### 과제 2: 성능 고려 (심화)
- 만약 수천 개의 디바이스에서 동시에 데이터가 들어온다면 어떻게 처리해야 할까요?
- `@Async`를 사용하거나, 메시지 큐(RabbitMQ, Kafka)를 도입한다고 가정하고 설계를 개선해보세요 (구현은 선택).

- [ ] 전체 시스템의 데이터 흐름을 설명할 수 있다.
